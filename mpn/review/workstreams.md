# Suggested workstreams

Repeated requirements are grouped here; each linked benchmark table has the full justification and evidence. Each action identifies the configuration, implementation or tailoring needed.

| Workstream | Needs-work rules | First action |
|---|---:|---|
| account-access-certification | 1 | The GitHub organization owner and Horizon engineering owner certify the protected Nov10 entitlement snapshot, justify each privileged role, record approved changes and review again within three months. |
| account-lifecycle | 6 | Gallatin sets Core Keycloak realmInitEnv.ACCOUNT_INACTIVITY_DAYS="35" in its MPN Core override. For an existing uds realm, enable Workflows > disable-inactive-users and set disable-user.after=35d through a controlled AdminConsole/API migration; redeploying the import Secret alone does not apply it. Preserve approved emergency/service exceptions; no duplicate Horizon lifecycle service. |
| account-recovery-procedure | 1 | Finalize and adopt the prepared identity-verification, authorized-unlock and audit-record procedure for Gallatin-operated UDS. Obtain documented MPN ISSO and ISSM approval and retain the approved version. Use the approved procedure for account unlocks and retain records showing identity verification and authorized recovery. |
| application-auditing | 33 | Confirm the desired privileged-function audit controls and event catalog, including the STIG minimum of the specific action and event date/time. Map each selected operation to existing UDS, role-audit and database-provenance records. Implement missing desired controls and actor/target/outcome records where required, correlate them with central collection, and verify the selected privileged operations produce the required records. |
| audit-alert-routing | 33 | Enable centralized account-creation alerts, configure named SA and ISSO recipients, and create a test account to verify both recipients receive notification. Retain the routing configuration and delivery-test evidence. Do not claim the enterprise user-management N/A exception without evidence that the assessed deployment satisfies that condition. |
| audit-review-procedure | 1 | Gallatin SRE and the designated security reviewer perform the prepared Loki/Grafana event review, disposition exceptions, record its date and set the next review due under the quarterly policy. |
| central-log-integrity | 1 | Map an accepted immutable/authenticated centralized storage or log hash/sign control to the record lifecycle, or enable it centrally; do not implement per-API duplicate log signing. |
| classification-guide | 1 | Identify the existing program/mission classification guide and the sections covering Horizon data. Add application-specific guidance only for uncovered data elements, then record the guide reference. |
| classified-crypto | 4 | Check the actual encryption against the official non-SAMI/SAMI requirements. Credit the delivered validated modules where allowed; use NSA-validated Type1 protection where the check requires it. |
| compliance-package | 7 | Document MPN application data elements and categories, the protection requirements for each, and the controls that implement those requirements. Apply mission/contract-specific classification and handling decisions to the existing architecture and corporate policies; retain the completed mapping and mission-owner confirmation. |
| continuous-vulnerability-management | 1 | Map Gallatin’s recurring MPN scanning service to the fixed delivered image inventory, or configure a scheduled rescan/cadence with retained results; do not duplicate the existing build scans. |
| data-backup-restore | 4 | Attach an accepted platform data-backup/restore service or configure PostgreSQL/PVC data protection and secure restore verification. |
| data-label-policy | 1 | Set the MPN data classification and provide the required application/report markings or exact permitted manual procedure/tailoring. |
| database-account-policy | 1 | Set approved service/admin per-role connection limits, with service-pool allowances; do not force2 if approved service-account limits differ. |
| database-auditing | 19 | Enable the required native connection/disconnection/privileged/direct-access event selection and contextual fields, with data/performance/redaction review; one shared audit workstream covers these rows. |
| identity-policy | 18 | Implement a supported previous-successful-logon date/time display through the shared UDS identity flow or Horizon UI, using existing login events where appropriate. Verify with successive successful logins that the displayed value identifies the preceding successful application access rather than the current login. Retain implementation and verification evidence. |
| mpn-host-storage-encryption | 1 | Commit the MPN control-plane EncryptionConfiguration (nonidentity encryption provider first) or supported distribution equivalent, rotate/migrate existing Secret storage after enablement, and bind Core identity database/PVC/node disks to the same encrypted-host design. Separate key administration from application identities. |
| mpn-network-profile | 2 | Define the approved MPN classification-to-destination information-flow policy and local model service. Configure allowed destinations and ports in the existing UDS Package policies and model settings. Inventory relevant classifier, inference and export paths; verify they enforce the approved flow policy, and address uncovered paths where required. Test labeled data against allowed and prohibited destinations and retain results. Do not treat the one classifier gate as proof of complete coverage. |
| mpn-storage-integrity | 3 | Define the sensitive/PII/classification data scope and select an approved authenticated-integrity storage boundary for its live database volume; a supported host dm-crypt+dm-integrity authenticated mode is one existing implementation option, not an instruction to reformat the current disk. Use existing AES-GCM object storage for object ciphertext and signed authenticated backup manifests for offline archives. Retain DB role restrictions separately. Do not credit plain diskSSE/AES-XTS, PostgreSQL page checksums or RBAC as cryptographic integrity, and do not build custom encryption for every database page. Keep this work open until the selected provider/host integrity setting or accepted scope mapping is committed. |
| mpn-storage-protection | 6 | Create one Gallatin-owned mpn-encrypted StorageClass backed by approved encrypted disks/volumes; set PostgreSQL persistence.storageClassName (not storageClass), bind SeaweedFS PVC explicitly and protect Core identity database/PVCs. Encrypt node OS/temp/cache and API Secret/datastore storage too. Keep the existing database/object-store products; use the selected host provider rather than a new storage cluster. Enable the existing SeaweedFS4.52 server flags -filer.encryptVolumeData and -s3.encryptVolumeData; retain filer metadata/keys on the encrypted protected volume. New writes use the existing AES-GCM path; migrate/rewrite existing objects deliberately. This supplements encrypted host/PVC storage and does not require every API to implement encryption. Apply the separate integrity step to the defined protected data set. |
| nats-auth-crypto-module | 1 | Route the NATS client/callout authentication signature operations through a validated approved-mode implementation, or obtain explicit accepted cryptographic-boundary tailoring for the existing protected mesh path. Credit current UDS/OIDC FIPS controls. |
| notice-banner | 6 | Enable Core realmInitEnv.TERMS_AND_CONDITIONS_ENABLED=true and apply the equivalent TermsAndConditions required-action setting to the existing uds realm through a controlled update. Persist the desired configuration. Compare the shipped notice text with the official required wording and verify the banner is displayed before access through the assessed interactive login paths. Retain configuration and verification evidence; no new Horizon banner page is required. |
| pii-processing-metadata | 2 | Have the privacy/mission data owner approve the PII element/purpose matrix below. Reuse files.tags and propagated chunk metadata for document-level tags such as privacy.profile, privacy.authorized_processing and privacy.processing_purpose. Attach a versioned schema-level privacy profile to account identity fields in the API/schema data dictionary; implement and validate only the missing association/propagation needed by the approved scope. If field-level tags are required, add narrow schema metadata or a field-to-policy mapping, not a wholesale per-row schema rewrite. Verify the exact data-tag interpretation with the assessor before treating a standalone document as an attached tag. |
| pki-authentication | 2 | Gallatin configures the approved required-card authentication path in Core: X509_AUTH_ENABLED=true and, for a certificate-only policy, USERNAME_PASSWORD_AUTH_ENABLED=false and SOCIAL_AUTH_ENABLED=false; apply equivalent existing-realm flow changes through controlled AdminConsole/API. Preserve approved emergency access and distinguish privileged PIV-card eligibility from personal CAC. These are existing provider flows, not new Horizon authentication features. |
| pki-trust | 7 | Gallatin uses Core CRL packaging/mount support, sets realmInitEnv.X509_CRL_CHECKING_ENABLED="true", X509_CRL_ABORT_IF_NON_UPDATED="true" and X509_CRL_RELATIVE_PATH to mounted approved files, and updates the existing dod-cac authenticator where necessary. Refresh the CRL data image/volume before expiry. Keep OCSP fail-closed; disable OCSP only for an approved disconnected CRL alternative. No custom Keycloak cache or API code. |
| ppsm-authorization | 2 | Ian/Gallatin SRE derives the external-enclave flow rows from the selected MPN overlay and existing System Impact Assessment; the security lead routes them to the MPN network/PPSM authority for CAL compliance review and approval. |
| registry-lifecycle | 1 | Add uds zarf tools registry prune to Gallatin’s MPN post-upgrade maintenance procedure/job after successful deployment, with a deliberate retained rollback-package/image policy and explicit confirmation before deletion. The tool preserves images referenced by current Zarf packages; do not blindly prune unreferenced images still needed for rollback. Track this as one shared registry lifecycle task. |
| registry-transport | 1 | In Gallatin’s MPN bootstrap, choose Zarf init v0.86.0 proxy mode via uds zarf init --registry-mode=proxy (with the pinned init artifact); this enables built-in cross-node mTLS with minimumTLS1.2. If alpha proxy mode is unsuitable, configure an external trusted TLS1.2+ registry explicitly. Do not deploy the unchanged HTTP NodePort default. Plan an initialization migration for an existing cluster instead of treating this as an in-place harmless flag flip. |
| release-crypto-provider | 2 | Use a verified validated/approved-mode signing implementation or record approved signing-scope/risk tailoring; retain tool module provenance. |
| runtime-response | 1 | Configure an accepted Falco/security event-to-access-control response or record approvedtailoring for the exactautomated integration. |
| secret-delivery | 2 | Move affected secret consumers to protected file/vault delivery, or retain a formally accepted environment-delivery exception with the corresponding protection rationale. Reuse the shared secret-delivery workstream. |
| secure-development-training | 1 | Program management and security training owners add the prepared role-specific secure-SDLC module to ThreatSwitch, assign all application roles, record completion/assessment and refresh annually. |
| security-assessment-coverage | 2 | Add or attach a scoped active/fuzz security assessment for web/API and relevant parsers, reusing the existing CI artifacts and defect process. |
| session-policy | 10 | Gallatin security confirms the proposed maximum of one concurrent session per user. Gallatin SRE sets realmInitEnv.SSO_SESSION_MAX_PER_USER to the approved positive value and updates the existing uds-user-session-count authenticator config through AdminConsole/API where needed. Verify the applied realm enforces the approved maximum. The proposed value of 1 is not yet an approved or applied configuration. No Horizon session-limiter code is needed. |
| web-hardening | 1 | Disable nginx version disclosure in error bodies or use a generic error response while retaining existing gateway header stripping. |
| web-http-protocol | 1 | Document operationally necessary translation, HTTP1 request validation/smuggling controls and CATIII/accepted tailoring, or configure end-to-endH2 if required. |
