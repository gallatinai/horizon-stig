# Suggested workstreams

Repeated requirements are grouped here; each linked benchmark table has the full justification and evidence. Each action identifies the configuration, implementation or tailoring needed.

| Workstream | Needs-work rules | First action |
|---|---:|---|
| account-access-certification | 1 | In the post-classification verification pass, locate the latest accountable-owner certification of Horizon repository access, its date, scope and recorded decisions. Confirm reviews occur at least every three months and cover effective grants, including inherited/team privileges. Credit an existing current review; if absent or overdue, have the accountable owner review access, record retention/removal decisions and approved changes, and set the next review date. Retain controlled references rather than publishing personnel details. |
| account-lifecycle | 6 | Gallatin sets Core Keycloak realmInitEnv.ACCOUNT_INACTIVITY_DAYS="35" in its MPN Core override. For an existing uds realm, enable Workflows > disable-inactive-users and set disable-user.after=35d through a controlled AdminConsole/API migration; redeploying the import Secret alone does not apply it. Preserve approved emergency/service exceptions; no duplicate Horizon lifecycle service. |
| account-recovery-procedure | 1 | Finalize and adopt the prepared identity-verification, authorized-unlock and audit-record procedure for Gallatin-operated UDS. Obtain documented MPN ISSO and ISSM approval and retain the approved version. Use the approved procedure for account unlocks and retain records showing identity verification and authorized recovery. |
| application-auditing | 33 | Confirm the desired privileged-function audit controls and event catalog, including the STIG minimum of the specific action and event date/time. Map each selected operation to existing UDS, role-audit and database-provenance records. Implement missing desired controls and actor/target/outcome records where required, correlate them with central collection, and verify the selected privileged operations produce the required records. |
| audit-alert-routing | 33 | Enable centralized account-creation alerts, configure named SA and ISSO recipients, and create a test account to verify both recipients receive notification. Retain the routing configuration and delivery-test evidence. Do not claim the enterprise user-management N/A exception without evidence that the assessed deployment satisfies that condition. |
| audit-review-procedure | 1 | In the post-classification verification pass, confirm the designated ISSO/reviewer and responsibility boundary, obtain the applicable documented review cadence and existing dated MPN review records, and check that reviews occur within that interval and immediately upon system security events as required. Credit an existing accepted process. If absent, establish the scoped schedule/event-driven process, perform the review and retain reviewer/date/results and next-due records. Do not assign platform review execution to Gallatin without confirming ownership. |
| central-log-integrity | 1 | Map an accepted immutable/authenticated centralized storage or log hash/sign control to the record lifecycle, or enable it centrally; do not implement per-API duplicate log signing. |
| classification-guide | 1 | In the post-classification verification pass, identify the approved mission/program security classification guide and confirm with the classification authority that it covers Horizon data elements and the required classification, handling and declassification guidance. Retain an appropriate controlled reference and scope mapping. Ask the authority to resolve only uncovered elements; do not create or approve classification guidance on its behalf. Update the recommendation when coverage is supported. |
| classified-crypto | 4 | In the post-classification verification pass, confirm the mission data classification and protection requirements and identify the MPN/Gallatin responsibility boundary. Inspect actual module/solution/configuration evidence for the cryptographic tasks and data covered by this exact rule, credit supported inherited protection, and identify only uncovered application/configuration responsibilities. Check the actual encryption against the official non-SAMI/SAMI requirements. Credit the delivered validated modules where allowed; use NSA-validated Type1 protection where the check requires it. Retain a controlled scope/protection mapping and revise the recommendation where coverage is supported. |
| compliance-package | 7 | Document MPN application data elements and categories, the protection requirements for each, and the controls that implement those requirements. Apply mission/contract-specific classification and handling decisions to the existing architecture and corporate policies; retain the completed mapping and mission-owner confirmation. |
| continuous-vulnerability-management | 1 | In the post-classification verification pass, identify the actual deployed image/component inventory and responsible MPN/Gallatin vulnerability-management services. Inspect recurring scan configuration, coverage and dated results, including unchanged release images and applicable platform components. Credit existing services and CI scans; configure only confirmed recurring-coverage gaps, retain findings/results and link the existing remediation process. Do not infer continuous coverage from build scans alone or absence from a separate source ECR setting. |
| data-backup-restore | 4 | In the post-classification verification pass, locate existing MPN/Gallatin backup services, procedures, ownership agreements and execution/restore records. Credit supported existing coverage and assign only confirmed residuals to the responsible operator. Confirm the site disaster recovery plan includes Horizon-specific secure and verifiable recovery instructions, actual application-data restore coverage and special considerations inhibiting trusted recovery. Verify restore evidence and complete only missing procedures or mechanisms. Retain the applicable procedure, configuration and verification evidence, coordinated with V-222636. |
| data-label-policy | 1 | In the post-classification verification pass, obtain the mission classification guide and inspect actual screen, report and print/export marking capabilities and configuration. Verify the required top/bottom markings for common sensitive-data transactions and report output; apply the official highest-system-classification rule when a guide is absent. Credit existing supported capability and implement only confirmed gaps. Check any manual printed-output procedures against the exact technical-limit conditions and availability to users. Retain function-specific evidence and coordinate required labels with the data owner. |
| database-account-policy | 1 | Set approved service/admin per-role connection limits, with service-pool allowances; do not force2 if approved service-account limits differ. |
| database-auditing | 19 | Enable the required native connection/disconnection/privileged/direct-access event selection and contextual fields, with data/performance/redaction review; one shared audit workstream covers these rows. |
| identity-policy | 18 | Implement a supported previous-successful-logon date/time display through the shared UDS identity flow or Horizon UI, using existing login events where appropriate. Verify with successive successful logins that the displayed value identifies the preceding successful application access rather than the current login. Retain implementation and verification evidence. |
| mpn-network-profile | 2 | Define the approved MPN classification-to-destination information-flow policy and local model service. Configure allowed destinations and ports in the existing UDS Package policies and model settings. Inventory relevant classifier, inference and export paths; verify they enforce the approved flow policy, and address uncovered paths where required. Test labeled data against allowed and prohibited destinations and retain results. Do not treat the one classifier gate as proof of complete coverage. |
| nats-auth-crypto-module | 1 | Route the NATS client/callout authentication signature operations through a validated approved-mode implementation, or obtain explicit accepted cryptographic-boundary tailoring for the existing protected mesh path. Credit current UDS/OIDC FIPS controls. |
| notice-banner | 6 | Enable Core realmInitEnv.TERMS_AND_CONDITIONS_ENABLED=true and apply the equivalent TermsAndConditions required-action setting to the existing uds realm through a controlled update. Persist the desired configuration. Compare the shipped notice text with the official required wording and verify the banner is displayed before access through the assessed interactive login paths. Retain configuration and verification evidence; no new Horizon banner page is required. |
| pii-processing-metadata | 2 | Have the privacy/mission data owner approve the PII element/purpose matrix below. Reuse files.tags and propagated chunk metadata for document-level tags such as privacy.profile, privacy.authorized_processing and privacy.processing_purpose. Attach a versioned schema-level privacy profile to account identity fields in the API/schema data dictionary; implement and validate only the missing association/propagation needed by the approved scope. If field-level tags are required, add narrow schema metadata or a field-to-policy mapping, not a wholesale per-row schema rewrite. Verify the exact data-tag interpretation with the assessor before treating a standalone document as an attached tag. |
| pki-authentication | 2 | Verify the applicable privileged/nonprivileged PIV/CAC authentication policy, current UDS realm flows and any approved emergency-access exceptions. Use existing X509/PIV/CAC and MFA settings to enforce the required card-based path and remove unauthorized alternative flows for that scope. Persist desired values and apply equivalent existing-realm changes through a controlled update. Verify card-required authentication and required multifactor behavior rather than assuming enabling X509 alone proves MFA. Retain configuration, policy and test evidence; do not build another authentication service. |
| pki-trust | 7 | Confirm PKI-authentication scope and whether the exact SIPRnet/no-root-CA-access exception applies. For applicable scope, use existing Core CRL packaging/mount support, enable X509_CRL_CHECKING_ENABLED, configure approved local CRL paths and strict freshness, and update the existing realm authenticator through a controlled change. Establish CRL refresh before expiry. Verify valid, revoked and stale-CRL behavior during network/OCSP unavailability using an approved disconnected profile; preserve fail-closed protections and retain configuration and test evidence. |
| ppsm-authorization | 2 | In the post-classification verification pass, locate the actual current MPN submission/System Impact Assessment and its submission or approval references. Compare its interface rows against the assessed deployment and the V-222519 inventory, confirm the local-enclave boundary, and check external addresses, services, ports and protocols are included. Credit existing submitted coverage and update the recommendation where supported; supply only missing or changed Horizon interface details through the established MPN authority route. Do not treat every internal pod port as an external interface or duplicate a complete submission. |
| registry-lifecycle | 1 | In the post-classification verification pass, identify the actual registry owner and inspect lifecycle/retention policy, current approved image versions, running digests and cleanup records. Confirm outdated organization-defined images are removed in accordance with the exact rule while preserving explicitly approved rollback artifacts. Credit existing operator maintenance; configure only missing controlled post-upgrade cleanup and verify results. Do not run destructive pruning or change initialization merely to inspect coverage. |
| registry-transport | 1 | In the post-classification verification pass, identify the actual MPN image sources, staging/registry and node image-pull paths and their owners. Inspect deployed registry/runtime/bootstrap settings and verify TLS 1.2 or newer for the applicable transport paths from trusted sources. Credit an existing approved MPN registry. Configure only confirmed gaps using an appropriate supported secure path; assess migration impact before changing an initialized registry/bootstrap. Retain configuration and transport-verification evidence. |
| release-crypto-provider | 2 | In the post-classification verification pass, inspect the assessed release's exact Witness binary/build provenance, cryptographic module validation and approved-mode configuration, wrapper environment and actual signing path. Determine whether an existing validated provider or remote signing service already supplies the required boundary. Retain evidence and change the recommendation to Likely covered if supported. Recommend signing-path changes only if verification confirms a gap; preserve working artifact signing. |
| runtime-response | 1 | Configure an accepted Falco/security event-to-access-control response or record approvedtailoring for the exactautomated integration. |
| secret-delivery | 2 | In the post-classification verification pass, confirm current secret delivery and retrieve applicable MPN and other customer credential-delivery requirements to verify the reported possible conflict. Check consumer support for protected file/vault delivery and define customer-specific profiles if necessary. For the assessed MPN scope, migrate affected secret-as-environment consumers while preserving authentication, or retain a formally accepted exception with its rationale. Do not change shared defaults for every customer without resolving the conflicting requirements. Retain requirement references, profile scope and verification evidence. |
| secure-development-training | 1 | In the post-classification verification pass, confirm the applicable development-team/program roles with the program manager and training owner. Map existing annual courses to role-appropriate secure-development/SDLC content and check dated completion evidence for each required role. Credit qualifying existing training, assign only missing content or overdue completions, and retain controlled completion references and the annual refresh schedule. Do not publish personnel training records in the tracker. |
| security-assessment-coverage | 2 | In the post-classification verification pass, locate existing active vulnerability and fuzz-testing procedures, scanner settings and results for the assessed architecture/release. Check relevant web/API and parser/component coverage and the official requirement concerning critical vulnerabilities 21 business days or older. Credit supported existing tests; arrange or implement only missing assessment coverage, retain results/settings and track findings through the existing defect process. Confirm responsibility and approved test scope before any active deployment testing. |
| session-policy | 10 | Gallatin security confirms the proposed maximum of one concurrent session per user. Gallatin SRE sets realmInitEnv.SSO_SESSION_MAX_PER_USER to the approved positive value and updates the existing uds-user-session-count authenticator config through AdminConsole/API where needed. Verify the applied realm enforces the approved maximum. The proposed value of 1 is not yet an approved or applied configuration. No Horizon session-limiter code is needed. |
| web-hardening | 1 | In the post-classification verification pass, inspect the assessed nginx/gateway configuration and representative externally visible warning/error responses. Check server/version, patch/module and internal path disclosures in both headers and bodies. Credit existing minimization; address confirmed residuals with supported settings or generic error responses while preserving useful client diagnostics. Retain configuration and response evidence; avoid claiming default behavior proves the actual external response. |
| web-http-protocol | 1 | In the post-classification verification pass, inspect effective gateway/backend protocol selection and confirm whether HTTP/2 requests are downgraded. If so, determine whether downgrading can be disabled safely. If operationally necessary, document that necessity and test rejection of the malformed requests specified by the official check, including header newlines, colons in header names and spaces in methods. Retain configuration/test evidence and propose the supported CAT III disposition or accepted tailoring for review; do not silently classify it as compliant. |
