## MPN storage protection solution

Treat the eleven rules as four shared changes: host/keystore encryption, application storage binding, cryptographic integrity, and encrypted backup/restore. All are proposed **Needs work** recommendations; none assert that an unconfigured deployment already passes. Gallatin owns the implementation. The remaining provider/classification choices determine which implementation to commit, not whether a solution exists.

1. **Keep PostgreSQL and SeaweedFS.** Choose the existing host provider's encrypted disk/volume class and name the MPN binding `mpn-encrypted`. Set PostgreSQL `persistence.storageClassName`; `persistence.storageClass` does not drive its template. Add an optional `storageClassName` to the SeaweedFS PVC template or deliberately configure the cluster default. Cover Core identity DB, control-plane/datastore, node OS and temporary/cache storage; PVC encryption alone leaves temporary files and Secrets exposed at a different layer. Use API-server `--encryption-provider-config` or the distribution's supported encryption feature for Kubernetes Secrets, with a nonidentity provider first. Keys are separate from application/data-reader credentials.
2. **Enable object encryption already in the delivered product.** SeaweedFS4.52 has `-filer.encryptVolumeData` and `-s3.encryptVolumeData`; its existing cipher implementation uses AES256-GCM and rejects failed authentication tags. Expose and enable those server arguments rather than implementing crypto in every API. Protect filer metadata/chunk keys on the encrypted volume and include them in protected recovery material. Rewriting existing objects is needed to migrate old unencrypted content; toggling new writes is not retroactive. The exact4.52 upstream source establishes algorithm/flags, not the validated module path in the delivered Chainguard image. Keep encrypted block/storage protection in an approved module as the primary boundary; enable object AEAD as additional protection and bind its provider/module evidence before crediting it for a FIPS-specific check.
3. **Handle integrity explicitly.** Plain disk encryption/AES-XTS gives confidentiality; PostgreSQL page checksums detect corruption but are not cryptographic authentication. Existing SeaweedFS AES-GCM authenticates object ciphertext, with metadata/keys protected separately. Define the PII/classification/security-label data set and select an approved storage provider or supported host authenticated-integrity implementation for that live database scope. Linux already provides dm-crypt plus dm-integrity authenticated modes; use such a mode only where the chosen distribution/module supports the required approved operation and operational profile. This is a storage configuration/migration choice, not a proposal to add custom crypto to every DB page. Retain existing DB writer/admin restrictions as separate authorization controls. Signed authenticated backup manifests protect offline copies; they do not substitute for live-volume integrity. Keep these rules Needs work until the chosen integrity setting or accepted data-scope/provider mapping is implemented.
4. **Encrypt before offline export.** Reuse the backup workstream to produce a consistent PostgreSQL backup/WAL set and SeaweedFS data+metadata set on encrypted scratch. Package them using an existing authenticated encryption format such as CMS AES256-GCM with a signed version/hash manifest, executed with a pinned approved provider/module. Copy only the encrypted authenticated archive to offline media. Keep decryption/recovery authority separately, including an offline-capable key recovery procedure. Validate the full envelope before publishing restored data from isolated encrypted scratch. A provider-encrypted cloud object downloads as plaintext; Azure KeyVault backup blobs also are not portable offline private-key escrow.

**Optional Azure realization, only if Azure/AKS is chosen:** use native Azure Disk CSI with `diskEncryptionSetID` where customer-managed keys are required, and choose node-pool `--enable-encryption-at-host` for host temporary/cache coverage. Native Azure managed disks have at-rest encryption already, so a new Rook/Ceph platform is unnecessary. A provider-neutral StorageClass binding still works for another MPN host. The existing app speaks S3; do not silently substitute a native Azure Blob endpoint as though protocols were interchangeable. Azure Blob can be an optional archive target with encryption and immutable completed backup objects, using a supported backup adapter. CMK/HSM is a requirement-dependent choice, not automatically required by every listed rule.

**Classification and module boundary:** this is a concrete baseline for stored-data confidentiality/integrity. Use the applicable validated cryptographic implementation for CUI/FIPS requirements. Classified MPN use requires its approved NSA/mission protection boundary; FIPS-capable disks or an AES algorithm name are not that approval. This dependency should remain visible in the mission-crypto decision, not leave all eleven technical solution rows unexplained.

**Acceptance from implementation artifacts:** committed host encryption settings; correct rendered PVC storage-class bindings; rendered SeaweedFS encryption flags; protected-key/recovery configuration with no real secrets committed; selected provider/host authenticated-integrity configuration; and backup/restore scripts that retain encryption outside the cloud. Negative fixtures should reject a modified encrypted object/archive and incorrect key. No live deployment, key creation, storage migration or backup export was performed.
